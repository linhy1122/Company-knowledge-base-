# 功能扩展 01 · 引用溯源——答案来源「跳转原文 + 高亮定位」

> 配套《后端实施方案.md》与《前端实施计划.md》。本文是对「来源 SourceCard 从『仅展示分块文本』升级为『跳转到该 chunk 在原文中的位置并高亮』」的落地细化。
>
> 涉及工程：`d:\Corpedia\backend\` + `d:\Corpedia\frontend\`。目标：点击答案来源卡片，弹窗内展示该 chunk 在原始文档中的上下文片段（前/后各带若干字符），并将该 chunk 区间高亮。

---

## 一、现状与缺口（已核实）

- **分块**：`Chunker.split` 按 500/100 字符窗口切分，chunkId = `doc-{documentId}-{idx}`，**只把 `strip()` 后的子串写进 Milvus `content`，没有记录它在原文中的字符区间**。
- **原文全文未持久化**：`DocumentPipelineService` 解析→清洗后即切块入库，**未保存清洗后全文**；磁盘只有原始上传文件（md/pdf/docx/txt 各异）。
- **来源展示**：`SourceCard.vue` 点击后调 `GET /api/documents/{id}/chunks`，按 chunkIndex 定位，弹窗仅显示该分块文本（`SourceCard.vue L22-L37`）。不含上下文、无高亮。

**结论**：要「跳转原文 + 高亮」，必须解决两件事：① 知道 chunk 在原文的**字节/字符区间**；② 前端能拿到**原文上下文文本**用于渲染与高亮。

---

## 二、方案选型

| 方案 | 做法 | 优劣 |
|---|---|---|
| A. 入库时记录偏移 + 持久化清洗后全文（**推荐**） | `Chunker` 计算并写入 `chunk_start/chunk_end`；清洗后全文存 `document.cleaned_text`；新增上下文接口 | 偏移精确、一次到位；代价=存量文档需重向量化一次 |
| B. 每次点击按确定性分块规则临时重切 | 接口内重读文件→清洗→`Chunker` 定位 chunkIndex 区间 | 免 schema 改动，但 pdf/docx 每次 Tika 重解析开销大，且清洗/读取需与入库完全一致，脆弱 |

**采纳方案 A**。分块本身是确定性的（500/100 窗口 + 换行优化），在切分点直接推算区间最稳，不依赖全文回查。

## 三、数据库变更（MySQL）

`document` 表新增一列，幂等迁移（沿用 `DatabaseMigrator` 模式）：

```sql
alter table document add column cleaned_text longtext null comment '清洗后全文（引用溯源用）；解析失败可为 null';
```

- `schema.sql` 建表语句同步加列（新建库直接含）。
- `DatabaseMigrator` 新增 `migrateAddDocumentCleanedText()`：查 `information_schema.columns`，缺失则 `alter table ...`（参考既有 `migrateAddMessageResponseMs`），启动日志 `document.cleaned_text 已补齐`。
- 实体 `KbDocument` 增加 `private String cleanedText;`（MyBatis-Plus 驼峰→蛇形自动映射）。

## 四、后端改造

### 4.1 `Chunker` —— 记录区间（核心）

`split(documentId, text, metadata)` 内部在切分时推算**strip 后子串在 `text` 中的首末索引**，写入 metadata：

```
切分窗口 [start, end)（substring 前）
子串 = text.substring(start, end).strip()
- 若子串非空：在 [start, end) 内定位 firstNonWs 与 lastNonWs
    chunk_start = start + 前导空白长度
    chunk_end   = start + 前导空白长度 + 子串.length()   // 即最后一个非空白字符后一位
  （用 strip 特性：前导空白长度 = strip 后前缀去除的字符数）
其他元数据键不变（chunk_index / document_id / title / department_id / permission_level / category / source）
```

`Constants` 新增键：`META_CHUNK_START="chunk_start"`、`META_CHUNK_END="chunk_end"`（int，存 Milvus metadata JSON 子字段，**无需建索引**，检索不需要）。

### 4.2 `DocumentPipelineService` —— 持久化清洗后全文

- 在 `runPipeline` 中，把 `cleaned` 写入 `doc.setCleanedText(cleaned)` 并随 READY 更新落库（在同一次 `updateById` 前设置）。
- `buildMetadata` 无需改动（区间在 Chunker 层加）。

### 4.3 `RagRetrieveService` / 来源透传

`toChunk` 从 metadata 读出 `chunk_start/chunk_end`，`RetrievedChunk` record 增加字段 `Integer chunkStart, chunkEnd`（可空，兼容旧数据）。

### 4.4 新接口：获取原文上下文

**目标**：输入 documentId + 区间，返回 chunk 上下文的「前/中/后」三段文本，前端可直接渲染并高亮。

```
GET /api/documents/{documentId}/context?chunkStart={cs}&chunkEnd={ce}&before=800&after=800
```

响应 `data`：

```json
{
  "documentId": 101,
  "filename": "01-01员工手册.md",
  "before": "…（chunk 之前的窗口，长度 ~before 字符，md 原文）…",
  "highlight": "（chunk 区间文本，即原文中被高亮部分）",
  "after": "…（chunk 之后的窗口，长度 ~after 字符）…"
}
```

实现要点：
- 数据源 = `document.cleaned_text`（`DocumentService` 内读取）。`cleaned_text` 为 null（存量未重向量化）→ 返回 400 `"原文尚未就绪，请先重向量化该文档"`，前端降级为原分块预览。
- 窗口切分算法（保持 md 结构完整 & 字符区间正确）：
  1. 从 `cleaned` 取 `[chunkStart, chunkEnd)` 为 `highlight`。
  2. `before = cleaned[max(0, chunkStart - before) .. chunkStart)`，尽量从行首开始（`lastIndexOf('\n')` 校正到就近换行），避免高亮上下文被切断句子。
  3. `after = cleaned[chunkEnd .. min(len, chunkEnd + after)]`，尽量到行尾（`indexOf('\n')`）。
  4. `before`/`after` 前后各补 `…` 占位（若被截断提示 前一页/后一页）。
- 权限：复用 `DocumentService.requireDoc(id)`（内含 `access.requireRead`），未登录/无权返回 401/403。
- 路由归属：新增 `DocumentController` 端点（或独立 `SourceController`，推荐放 DocumentController 保持一致）。

> 备选进阶（本期可不做）：md 渲染后再定位高亮有偏移问题（`v-html` 输出文本 ≠ 原始文本），故接口直接切分红 `highlight` 单独返回，前端用 `<mark>` 包住整段，规避字符级高亮在 Markdown 渲染下的漂移。

### 4.5 存量数据迁移

- 存量 READY 文档无 `chunk_start/chunk_end`（Milvus）与 `cleaned_text`（DB）→ 提供一次性重向量化：
  - 复用既有 `POST /api/rag/process/{documentId}` 或 kb 级 `reprocessAll(kbId)` 逐库触发；
  - 或提供管理脚本遍历全部 READY 文档调 `reprocess`（幂等，清旧 chunk 重建）。
- 说明成本：需重新 embedding（每库全量），一次性。

## 五、前端改造

### 5.1 API 封装（`src/api/kb.ts`）

```ts
export interface DocContext { documentId: number; filename: string; before: string; highlight: string; after: string }
export function getDocumentContext(id: number, p: { chunkStart?: number; chunkEnd?: number }, config?: { silent?: boolean }) {
  return http.get<DocContext>(`/documents/${id}/context`, { params: p, ...config })
}
```
`Source` 类型（`conversation.ts`）追加可选 `chunkStart?: number; chunkEnd?: number`。

### 5.2 `SourceCard.vue` 升级

- `openPreview`：优先使用 `source.chunkReady`（有 `chunkStart`）走 `getDocumentContext`；否则回退现有 `getDocumentChunks` 定位逻辑（兼容旧消息/旧接口）。
- 渲染：弹窗内
  - 有上下文：`before`/`highlight`/`after` 分别 `renderMarkdown`，其中 `highlight` 外再包 `<mark class="context-hl">`（element 主题高亮底色，`::mark` 黄色底 + 黑字）。三段不额外换行拼接，保持行文连续。
  - 无上下文（400）或 `cleaned_text` 未就绪：显示「原文尚未就绪」+ 提示「可在文档管理中重向量化」，仍展示该 chunk 文本。
- 顶部工具栏增加「显示源行区间：chunk @[start, end)」等信息（可选）。
- 新增样式 `.context-hl { background:#fff3b0; color:#333; border-radius:2px; padding:0 1px; }`（放组件 scoped）。

### 5.3 需求改动小结（前端清单）

- [ ] `SourceCard.vue` 上下文窗口 + `<mark>` 高亮 + 旧逻辑降级

## 七、验收

1. 新上传文档：提问 → 参考答案来源 → 点击来源 → 弹窗显示「前文 + 高亮的命中分块 + 后文」，高亮区清晰可见且与检索片段一致。
2. 存量文档：重向量化后同 ① 生效；未重向量化的文档点击来源走降级（仅分块文本 + 提示）。
3. 越权：无法访问该文档的用户调用 `context` 返回 403（复用 `requireDoc`）。
4. `md` 文档高亮不因 Markdown 渲染错位（高亮段整包 `<mark>`）。
5. `npm run build` 与后端启动（含迁移日志 `cleaned_text 已补齐`）通过。

---

## 八、风险与注意事项

| 风险 | 应对 |
|---|---|
| 存量文档需重新 embedding | 一次性 reprocess 全部；分块确定性 => 区间与重向量化后完全一致 |
| `cleaned_text` 大字段存储 | 仅存清洗后纯文本（≈解析文本量），LONGTEXT 足够；不做即删 |
| md 渲染导致字符级高亮漂移 | 后端切分红前后中三段，高亮整段 `<mark>`，不做字符级定位 |
| 旧消息 `sources` 无 offset | `chunkStart/End` 可空，前端回退旧逻辑 |

> 后续可扩展：按页（pdf 页码）高亮、双栏对照原文（左原文右分块）。
