# 功能扩展 03 · 多模型 / 多知识库切换

> 配套《后端实施方案.md》与《前端实施计划.md》。目标：用户在前端可选**回答用哪个 LLM 模型**、**检索用哪些知识库**（默认全量可选范围），并把选择持久化到会话。
>
> 涉及：`d:\Corpedia\backend\` + `d:\Corpedia\frontend\`。

---

## 一、现状与缺口（已核实）

- **模型**：`application.yml` 固定 `spring.ai.openai.chat.model=google/gemma-4-e4b`，Spring AI 2.0 自动装配**单个** `ChatModel`；`RagChatService` 用 `ChatClient.Builder.defaultTools(amapWeatherTool)` 构建唯一 ChatClient。无法运行时切换模型。
- **知识库检索**：`RagChatService.chat` → `PermissionService.buildVectorFilter(userId)`（仅部门+权限过滤），在**整个 collection** 里检索全部可达文档；前端无知识库选择入口。
- **元数据**：Milvus chunk metadata 有 `category`（=知识库名）、`document_id`，但**没有 `kb_id` 整数键**，做多知识库筛选需新增。

---

## 二、方案设计

### 2.1 多模型

- 数据源仍是 LM Studio（OpenAI 兼容）；在 **LM Studio 内加载多个模型**，每个对应一个 `OpenAiChatModel` Bean。配置改为**模型清单**：

```yaml
corpedia:
  models:
    default: google/gemma-4-e4b
    list:
      - { id: google/gemma-4-e4b, name: Gemma 4 (默认) }
      - { id: qwen2.5-7b-instruct, name: Qwen 2.5 7B }   # 示例，按 LM Studio 实际已加载 id 填写
```
- 新增 `ModelRegistry`（`@Component`）：基于同一 `spring.ai.openai.base-url/api-key` 为每个 id 构建 `OpenAiChatModel`（`OpenAiChatOptions.builder().model(id).temperature(0.2).build()`），并缓存 `ChatClient`（`ChatClient.builder().model(chatModel).defaultTools(amap, ...)`——在 Spring AI 2.0 中 `ChatClient.Builder.model(ChatModel)` 绑定具体模型）。
  - `getDefaultModelId() / listModels() / getClient(modelId)`；未知 id 回退默认。
- `RagChatService` 改为**按 modelId 选取 ChatClient**：`chat(userId, convId, question, modelId)` 内 `ClientProvider.getClient(modelId)`。原单一 `chatClient` 字段替换为依赖 `ModelRegistry`（`defaultTools` 统一挂在 registry 构建的统一客户端，避免工具注册重复）。
- 暴露模型列表：`GET /api/config/models` → `[ {id,name} ]`（默认第一项）。

### 2.2 多知识库

- **检索过滤按知识库选择**：新增 Milvus metadata 键 `kb_id`（int）。`buildMetadata` 写入 `doc.getKbId()`；`Constants.META_KB_ID="kb_id"`（**无需建索引**，过滤与权限表达式一起做 `in`）。
- `PermissionService` 新增重载：`buildVectorFilter(userId, List<Long> kbIds)`。逻辑：
  - `SYS_ADMIN`：kbIds 有值 → `kb_id in [...]`；否则 null（全量）。
  - 其他用户：在既有 `department_id in [0, dept] && permission_level <= level` 上，若 kbIds 有值 → **追加 `&& kb_id in [...]`**（交集，仍受权限约束）。
  - 前端传的 kbIds 需在服务端二次过滤——只保留该用户可见的知识库（查 `KbService.list()` 或用 `KnowledgeBaseMapper` 按 id 校验可读），防止越权指定不可见库。
- **选择持久化**：会话级记录 `modelId` / `kbIds`。
  - `conversation` 新增列 `model_id varchar(64) null`、`kb_ids json null`（幂等迁移）。
  - 前端设好选择 → `PUT /api/conversations/{id}`（功能02 已扩展支持 modelId/kbIds）保存。
  - 提问时 `SendMessageRequest` 可带 `modelId/kbIds`（临时覆盖），缺省回落到会话已存值，再回落到全局默认。

### 2.3 打通主链路（`RagChatService.chat`）

```
签名扩展：chat(userId, conversationId, question, modelId, List<Long> kbIds)
1) filter = permission.buildVectorFilter(userId, kbIds)
2) client = modelRegistry.getClient(modelId)
3) retrieve(question, topK, filter) → 阈值/rerank → client prompt(...)   // 与现逻辑一致
```
- 阈值校准提醒：**不同模型/语料下 `similarity-threshold` 需重新实测校准**（见「风险与注意事项」，沿用阶段4 校准方法，`Test\知识库测试问题集.json`）。

## 三、数据库变更

```sql
alter table conversation add column model_id varchar(64) null comment '会话使用的 LLM 模型 id；空=默认';
alter table conversation add column kb_ids json null comment '会话绑定的知识库 id 列表(JSON)；空/[]=默认全量';
```
- `schema.sql` 建表语句同步加列；`DatabaseMigrator` 幂等补齐（沿用既有步骤）。
- 实体 `Conversation` 增 `private String modelId; private String kbIds`（JSON 字符串，MyBatis-Plus 直接映射 varchar/json 均可）。

## 四、接口清单

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/config/models` | 可用模型列表 `[{id,name}]` |
| PUT | `/api/conversations/{id}` | 保存 title / modelId / kbIds（功能02 联用） |
| POST | `/api/messages` | body 增可选 `modelId?`、`kbIds?`（缺省回落会话值/默认） |

`SendMessageResultVO` / `MessageVO` 不变（可选补 `modelId` 回显）。

## 五、前端改造

### 5.1 模型选择

- `api/config.ts`：`getModels()` → `GET /api/config/models`。
- `ChatView` 顶栏下拉「回答模型」：进入会话时从会话 `modelId`（有则）或默认；切换 → 即时 `updateConversation(id,{modelId})` 保存；新会话未保存前仅本次生效。
- 发送 `sendMessage` 透传当前 `modelId`（可选）。

### 5.2 知识库选择

- `api/kb.ts`：`listAccessibleKb()`（复用 `GET /api/kb`，后端已按权限过滤）。
- `ChatView` 顶栏「知识库」多选（`el-select multiple`，选项=可达知识库）：选择变化 → `updateConversation(id,{kbIds})` 保存；默认全选（空=后端视为全量）。
- 切换知识库时清空当前消息流并提示「已切换检索范围，请重新提问」（避免旧答案误导）。
- 发送同时携带 `kbIds` 保证一致性。

### 5.3 类型

`Conversation` 类型增 `modelId?: string | null; kbIds?: number[] | null`；`sendMessage` 入参增可选字段。

## 六、验收

1. 模型列表来自 `/api/config/models`，前端可切换；同一问题用不同模型回答（至少能发出不同模型的请求并返回）。
2. 指定某知识库提问：答案来源仅限该库文档；跨库问题在只选其一库时不应引用另一库。
3. 权限约束：财务用户即便手动传入研发部 `kbId`，后端校验后仍不可检索该库内容。
4. 选择持久化：切会话后 modelId/kbIds 恢复；发送不带参数时回落会话/默认值。
5. 多模型切换后阈值不误拒：用测试问题集重新校准 `similarity-threshold`。

## 七、风险与注意事项

| 风险 | 应对 |
|---|---|
| LM Studio 未加载对应模型 id | `GET /config/models` 只返回 yaml 中登记且在 `/v1/models` 存在的 id；启动时/接口处校验，不存在则告警并剔除 |
| 不同模型得分分布差异致误拒/误答 | 切换模型后按既有方法重测校准阈值；可在 yaml 记录各模型建议阈值（本期仅提示） |
| 前端传不可见 kbId 越权 | 后端二次校验 kbIds ⊆ 用户可见库，越权停留为按可见库交集 |
| 存量 chunk 无 `kb_id` | 需一次性 reprocess 重建（清旧 + 重 embedding），与功能01 迁移同批处理 |

---

## 八、与其他扩展计划的关系

- 本功能新增的 `PUT /conversations/{id}`（保存 modelId/kbIds）与**功能02 会话管理**共用同一端点与 DTO，建议同阶段实现。
- `kb_id` 重向量化迁移与**功能01 引用溯源**（需补 offset + cleaned_text）可合并为一次全量 reprocess，降低工作量。
